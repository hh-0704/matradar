# 운영

1인 운영 기준으로, **사람이 기억하지 않아도 잘못된 배포가 나가지 않고, 문제가 생기면 먼저 알 수 있게** 만드는 데 집중했습니다.
서버 주소·경로·버킷 이름·알림 주소·제한 수치 같은 운영 식별자는 적지 않습니다.

## 브랜치와 배포

```
develop ──push──▶ CI ──▶ (PR / 병합) ──▶ main ──▶ 백엔드: 배포 스크립트 실행
                                                └─▶ 프론트: Pages 가 main 을 자동 빌드·배포
```

### 백엔드

- **CI**(GitHub Actions)는 push·PR 마다 두 가지를 돌립니다.
  - 테스트 — 단위·통합 테스트. 통합 테스트는 Testcontainers 로 실제 MySQL·Redis 를 띄웁니다. 운영과 같은 힙 크기의 사진 메모리 테스트도 따로 돕니다.
  - 운영 이미지 빌드 — 운영과 같은 Dockerfile 로 이미지를 만들어 봅니다. 이미지를 아무도 빌드해 보지 않은 채 배포하는 공백을 막습니다.
- **배포 스크립트**는 운영자가 직접 실행합니다.
  1. 로컬 HEAD 가 `origin/main` 과 같은지, 그 커밋의 CI 가 성공했는지 확인합니다. 아니면 시작하지 않습니다.
  2. git 이 추적하는 파일만 서버로 보냅니다. 작업 트리의 잡동사니가 운영에 섞이지 않습니다.
  3. 직전 이미지를 보관한 뒤 새 이미지를 빌드합니다.
  4. 기동합니다. 프록시 설정이 바뀌었으면 문법 검사를 먼저 하고, 실패하면 멈춥니다.
     실행 중인 이미지 ID 를 새 빌드와 비교해 강제로 재생성합니다([판단 사례 2](./decisions.md#2-성공-메시지를-믿지-않고-결과를-확인하게-바꿨다)).
  5. 헬스체크가 실패하면 **직전 이미지로 자동 롤백**합니다.

### 프론트엔드

- Cloudflare Pages 의 빌드 명령은 타입 검사 · 린트 · 테스트를 통과해야 운영 빌드로 넘어갑니다.
- 운영 빌드는 env 누락, 개발용 화면 포함, mock 포함, 보안 헤더(CSP) 치환 누락을 **산출물을 열어** 검사하고, 하나라도 걸리면 배포하지 않습니다.
- 배포 전 검증은 새로 clone 한 디렉터리에서 합니다. 로컬에만 있는 파일이 결과를 바꾸는 일을 막습니다.

## 엣지와 남용 방지

- Cloudflare 프록시 + Origin 인증서(Full strict), HSTS, `www` → 루트 도메인 리다이렉트.
- 남용 방지는 층마다 따로 겁니다. 한 층이 뚫려도 다음 층이 있습니다.

| 층 | 무엇을 |
|---|---|
| nginx | IP 단위 요청·동시 연결 제한. IPv6 는 /64 로 묶습니다 |
| 애플리케이션 | 관리자 로그인 시도, 게스트 발급 — 역시 IP(/64) 단위 |
| 자원 | 사진 처리는 예상 메모리 예산 안에서만 동시에 돕니다([판단 사례 3](./decisions.md#3-사진-처리-동시성을-건수가-아니라-메모리로-묶었다)) |

## 백업과 감시

- 매일 DB 를 덤프해 **객체 스토리지(Cloudflare R2)** 로 올립니다. 업로드 뒤 원격 크기를 로컬과 대조하고, 보존 기간이 지난 건 정리합니다.
  백업 파일은 소유자만 읽을 수 있게 만듭니다.
- 백업 작업의 시작·성공·실패를 외부 하트비트 감시로 보냅니다. 실패했을 때뿐 아니라 **아예 돌지 않았을 때도** 알림이 옵니다.
- 복원 연습을 해 봤고, 절차를 문서로 남겼습니다.
- VPS 자체의 스냅샷 백업을 별도로 둡니다.
