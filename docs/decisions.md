# 판단 사례

만들면서 내린 판단 중 세 가지입니다. 무엇을 골랐는지보다 **왜 그렇게 골랐는지**를 적었습니다.

---

## 1. 탐지는 판정이 아니라 우선순위로 설계했다

**상황.** 광고·체험단 리뷰를 걸러내는 게 서비스의 핵심이라, 의심스러운 계정을 자동으로 막고 싶은 유혹이 컸습니다.

**판단.** 자동 제재를 두지 않았습니다. 탐지 점수는 운영자가 먼저 볼 것을 정하는 **검토 우선순위**로만 씁니다.

**이유.**
- **오탐 비용이 비대칭입니다.** 정상 사용자를 잘못 제재하면 그 사람은 이유도 모른 채 떠나고, 리뷰 서비스에서 가장 귀한 자원인
  "꾸준히 쓰는 사람"을 잃습니다. 어뷰저 하나를 놓치는 비용은 그보다 작습니다.
- **삭제보다 희석이 안전합니다.** 가게 평점은 작성자 신뢰도를 반영한 가중 평균입니다. 의심스러운 리뷰를 지우는 대신 평점에 주는
  힘을 줄이면, 판단이 틀렸을 때의 피해가 삭제보다 작고 되돌리기도 쉽습니다.
- **탐지와 조치를 나누면 둘 다 바꾸기 쉽습니다.** 점수기를 손봐도 조치 흐름은 그대로고, 조치 정책을 바꿔도 점수기는 그대로입니다.
  조치는 운영자의 명시적 행동으로만 일어나고, 모든 조치에 되돌리는 길이 있습니다.

구조는 [review-integrity.md](./review-integrity.md)에 있습니다. 탐지 방식 자체는 공개하지 않습니다.

---

## 2. "성공" 메시지를 믿지 않고 결과를 확인하게 바꿨다

첫 운영 배포를 하면서 **에러 없이 끝났는데 실제로는 실패한** 경우를 세 번 만났습니다. 셋 다 같은 방식으로 고쳤습니다.
**종료 코드나 완료 메시지가 아니라 결과물을 직접 확인합니다.**

### 백업이 업로드 없이 성공했다

첫 수동 백업이 "외부 업로드 완료"를 찍고 exit 0 으로 끝났는데, 객체 스토리지는 비어 있었습니다. 설정으로 받은 업로드 명령 뒤에
덤프 경로를 붙이는 방식이라 인자 순서가 뒤집혀 **올리기가 아니라 내려받기 명령**이 됐고, 그 명령은 아무것도 하지 않고 성공으로 끝났습니다.

- 업로드 명령은 스크립트가 직접 조립하고, 업로드 직후 **원격 객체의 크기를 다시 조회해 로컬 파일 크기와 대조**합니다. 다르면 실패로 끝냅니다.
- 고친 뒤에는 실패 경로(무동작 exit 0, 크기 불일치, 도구·키 없음 등)를 하나씩 일부러 만들어 전부 실패로 끝나는지 확인했습니다.
- 실패는 물론 **아예 실행되지 않은 날**도 알 수 있게 외부 하트비트 감시(dead man's switch)를 붙였습니다. 시작·성공·실패를 각각 보내고,
  정해진 시간 안에 성공 신호가 없으면 알림이 옵니다.
- 백업은 복원해 봐야 백업입니다. 올라간 파일을 다시 받아 임시 DB 컨테이너에 복원하고, 테이블별 행 수가 원본과 같은지 확인했습니다.

### IPv6 사용자는 IP당 제한을 우회할 수 있었다

로그인 시도·게스트 발급 같은 IP 단위 제한이 주소 하나를 키로 세고 있었습니다. IPv6 사용자는 보통 /64(주소 2^64개)를 통째로 받으므로,
그 안에서 주소를 바꿔 가며 보내면 제한이 사실상 사라집니다. 서비스가 IPv6 로도 열려 있다는 걸 배포하면서 확인했습니다.

- nginx 와 애플리케이션 **두 층 모두** IPv6 를 /64 단위로 묶었습니다(`RateLimitClientKey`). 한쪽만 바꾸면 두 층의 키가 어긋납니다.
- nginx 쪽은 정규식 map 이라 틀리기 쉬워서, 무작위 IPv6 주소를 만들어 **nginx 설정에서 뽑은 키와 기준 구현의 /64 계산을 대조하는
  검증 스크립트**를 만들었습니다. 압축 표기, 앞자리 0, IPv4-mapped 주소 같은 표기 차이를 전부 같은 키로 모읍니다.

### 배포가 "완료"를 찍었는데 옛 버전이 돌고 있었다

배포 스크립트는 새 이미지를 빌드하고 컨테이너를 올렸다고 보고했지만, 실제로는 직전 이미지가 계속 돌고 있었습니다. 이미지 태그는 그대로고
내용만 바뀐 경우, compose 가 "변화 없음"으로 보고 컨테이너를 다시 만들지 않았습니다. 그때는 앱 코드가 같아 실제 피해는 없었습니다.

- 실행 중인 컨테이너의 **이미지 ID 와 방금 빌드한 이미지 ID 를 직접 비교**해, 다르면 강제로 다시 만듭니다.
- 배포 확인 단계에 "실행 중 이미지 = 새 빌드" 검사를 넣었고, 실패 시 직전 이미지로 돌아가는 롤백도 같은 방식으로 강제합니다.

## 3. 사진 처리 동시성을 건수가 아니라 메모리로 묶었다

**상황.** 사진 업로드는 서버에서 디코드 → 합성 → JPEG 재인코딩을 거칩니다. 이 과정의 메모리가 사진마다 크게 다릅니다.
프론트가 줄여 보내는 2048px JPEG 는 약 34MB 지만, 업로드 상한 크기의 16비트 PNG 는 약 270MB 입니다.

**처음 떠오르는 답 — 동시 처리 N장 제한 — 은 이 차이를 다루지 못합니다.** N 을 큰 사진 기준으로 잡으면 리뷰 한 건의 사진 5장(병렬 업로드)도
줄을 서고, 작은 사진 기준으로 잡으면 큰 사진 몇 장으로 힙이 넘칩니다.

**판단.** 예상 메모리를 예산으로 삼았습니다(`ImageProcessingLimiter`, `ImageMemoryEstimator`).

- 1MiB 를 한 단위로 하는 **공정(FIFO) 세마포어**에서 사진마다 예상 메모리만큼 가져갑니다. 예상치는 이미지 **헤더만 보고 디코드 전에**
  계산합니다.
- 형식별 픽셀당 바이트는 추측이 아니라 **측정값**입니다. 힙을 줄여 가며 처리가 성공하는 최소 힙을 찾았고, 그 값을 올림해 썼습니다.
  과소 추정은 OOM 이고 과대 추정은 대기일 뿐이라, 애매하면 큰 쪽으로 둡니다.
- **대기열에 상한을 둡니다.** 무제한으로 기다리게 하면 요청 스레드가 묶여 사진과 무관한 API 까지 멈춥니다. 대기 인원이 차 있으면 바로
  503 + `Retry-After` 를 돌려주고, 프론트는 같은 사진으로 다시 시도합니다.
- 공정성을 지키려고 대기 시간 0 의 `tryAcquire(permits, 0, unit)` 를 씁니다. 인자 없는 `tryAcquire` 는 줄을 새치기해서, 작은 요청이
  계속 새치기하면 큰 요청이 굶습니다.
- 상한 크기 사진 한 장이 예산을 넘는 설정이면 그 사진은 영원히 처리되지 못하므로, **설정 실수를 부팅 시점에 막습니다.**
- 운영과 같은 힙 크기로 사진 처리를 돌리는 메모리 테스트를 CI 에 따로 두었습니다.
